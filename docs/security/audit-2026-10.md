## Находки

### 1. Нет ограничения размера тела запроса — средняя, исправлено в этом PR
- Где: `server/src/api.ts` (все `await c.req.json()`).
- Сценарий: любой настоящий пользователь Telegram шлёт POST с телом в сотни мегабайт; Hono читает его целиком в память.
- Влияние: исчерпание памяти, отказ в обслуживании для всех.
- Исправление: `bodyLimit` 256 КБ на `/api/*`, ответ 413. Тест: «an oversized JSON body is refused with 413».

### 2. Запасные токены привязки чата — средняя, исправлено в этом PR
- Где: `server/src/chatLink.ts`, `attachChat`; `server/src/bot.ts:165` (`/balance` создаёт токен при каждом вызове в непривязанном чате).
- Сценарий: в непривязанном чате несколько раз вызвали `/balance`, получили несколько токенов. Админ привязал чат по одному, остальные оставались действительны 24 часа. Любой участник чата, нажавший кнопку из старого сообщения, привязывал чат к своей группе и тем самым отвязывал чат от группы админа.
- Влияние: тихая подмена группы, в которую бот пишет ленту и чей баланс показывает `/balance`. Данных чужой группы атакующий этим не получает.
- Исправление: при привязке помечаются использованными все неиспользованные токены этого чата. Тест: «spare tokens of a chat die when one of them is used».

### 3. Нельзя убрать участника с Telegram, нельзя сменить приглашение — средняя, предложение
- Где: `api.ts` — `DELETE /groups/:id/members/:memberId` отвечает 409 `memberHasTelegram`; эндпоинта смены `invite_code` нет.
- Сценарий: ссылка-приглашение попала не туда (пересланное сообщение, ссылка в чате с кнопкой «Вступить»). Посторонний вступает, видит все траты и реквизиты участников, и владелец не может его исключить. Архивная группа тоже принимает вступающих.
- Влияние: утечка данных группы без возможности её закрыть.
- Предложение: эндпоинт `POST /groups/:id/invite/rotate` (только владелец), исключение участника владельцем (с сохранением истории: `user_id = NULL`), опциональный запрет вступления в архивную группу.

### 4. `/api/rates`: будущие даты и кэш — средняя, частично исправлено
- Где: `api.ts` (`GET /rates`), `rates.ts` (`todayMemo`, `fetchDay`).
- Сценарий: запросы с `date=2099-xx-xx` и разными датами. Каждая новая дата дает до 8 запросов к cbr-xml-daily.ru и запись в `todayMemo`, которая никогда не чистится. 120 запросов в минуту с одного аккаунта.
- Влияние: рост памяти, нагрузка на внешний сервис (риск блокировки IP).
- Исправлено: даты дальше чем на 2 дня вперёд отвечают 400. Тест: «rates: far-future dates are refused».
- Остаётся: ограничить `todayMemo` (удалять устаревшие записи); для прошлых дат запись в `rates` ограничена историей ЦБ (порядка 12 тысяч дат), это приемлемо; отдельный лимит на `/rates` (например 20 в минуту).

### 5. Привязка чата без проверки прав в чате — средняя, предложение
- Где: `api.ts` `POST /chat-links/:token/attach`; `bot.ts` (`my_chat_member`, `/balance`).
- Сценарий: токен лежит в кнопке, которую видят все участники чата. Привязать может любой, у кого есть токен, даже не будучи админом и не состоя в чате (токен можно переслать). `/unlink` при этом требует админа, привязка — нет.
- Влияние: рядовой участник чата определяет, какая группа привязана; через `/balance` в чат попадают балансы привязанной группы (для группы атакующего это его собственные данные).
- Предложение: при выдаче токена и при `attach` проверять через `getChatMember`, что пользователь админ чата; в `/balance` в непривязанном чате переиспользовать действующий токен вместо создания нового; чистить `chat_links` с истёкшим сроком (сейчас таблица только растёт).

### 6. Нет квот и пагинации — низкая, предложение
- Где: `api.ts` (`POST /groups`, `/expenses`), `repo.ts` `loadLedger`, `groupDetail`.
- Сценарий: один аккаунт создаёт до 120 записей в минуту без верхней границы; `groupDetail` и `groupsForUser` каждый раз читают и отдают все траты группы; `node:sqlite` синхронный, большая группа блокирует event loop для всех.
- Предложение: квоты (групп на пользователя, трат на группу, шаблонов), пагинация трат, чистка старых записей `activity`.

### 7. 500 на хэше с не-ASCII символами — низкая, исправлено в этом PR
- Где: `server/src/auth.ts:27`. Длина строки сравнивалась в символах, а `timingSafeEqual` проверяет байты и бросал `RangeError`.
- Влияние: не обход подписи, а шум в логах и 500 вместо 401.
- Исправление: хэш должен соответствовать `^[0-9a-f]{64}$`. Тест: «initData: a non-hex or multi-byte hash gives null».

### 8. `DEV_AUTH` в продакшене — низкая, предложение
- Где: `config.ts` (`devAuth: env.DEV_AUTH === '1'`), `api.ts` (схема `dev <id>`).
- Состояние: по умолчанию выключен, в `docker-compose.yml` не передаётся, при включении пишется предупреждение. Но при случайном `DEV_AUTH=1` любой человек входит как любой пользователь.
- Предложение: игнорировать `DEV_AUTH` при `NODE_ENV=production`. Для этого придётся поправить CI: smoke-тесты образа (`docker.yml`) запускают образ с `DEV_AUTH=1` и `Authorization: dev 1`; нужен отдельный явный флаг вроде `ALLOW_DEV_AUTH_IN_PROD=1` только в smoke-тестах. Изменение не мелкое, поэтому не вошло в PR.

### 9. Заголовки и CSP — низкая
- Где: `app.ts`.
- Исправлено: `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`. Тест: «responses carry nosniff and no-referrer headers».
- Предложение: CSP (`script-src 'self' https://telegram.org`, `connect-src 'self'`, `frame-ancestors` под клиенты Telegram, `img-src` под `t.me`/`telegram-cdn`). `X-Frame-Options: DENY` ставить нельзя: Mini App открывается во фрейме веб-клиента Telegram. HSTS должен выставлять Traefik.

### 10. Telegram id и username участников — низкая, предложение
- Где: `repo.ts` `groupDetail` (`userId`, `username`, `photoUrl`).
- Веб использует `userId` только как признак «есть Telegram» (`Settings.tsx`).
- Влияние: любой участник группы видит числовые Telegram id остальных (id не секрет, но минимизация данных лучше).
- Предложение: отдавать `hasTelegram: boolean` вместо `userId`; `username` оставить для подписи.

### 11. Бот и экспорт без отдельных лимитов — низкая, предложение
- Где: `bot.ts` (обработчики `/balance`, `inline_query`, `/help`), `api.ts` `POST /groups/:id/export`, `/remind`.
- Лимит 120 запросов в минуту работает только для `/api`. Обработчики бота не ограничены (защищает лимит самого Telegram). Экспорт можно запускать до 120 раз в минуту, то есть отправлять файлы в личку и расходовать общий лимит бота. Напоминания: один на пару за 24 часа, это хорошо.
- Предложение: лимит на экспорт (например 5 в минуту), простой счётчик на `/balance` для чата.

### 12. Логи содержат данные пользователей — низкая, предложение
- Где: `bot.ts:297` `console.warn('sendMessage failed', e)`. У `GrammyError` есть `payload` с текстом сообщения (названия групп, суммы, имена).
- Токен бота в логи не попадает: ошибки сети grammY не содержат URL с токеном, в `index.ts`/`bot.ts` токен не печатается.
- Предложение: логировать `error_code` и `description`, а не объект целиком.

### 13. Некорректные числовые настройки — инфо
- Где: `config.ts`: `INIT_DATA_MAX_AGE=abc` даёт `NaN`, сравнение `> NaN` ложно, подпись не истекает; `RATE_LIMIT_PER_MIN=abc` отключает лимит.
- Предложение: `Number.isFinite(...) ? ... : default`.

### 14. Реквизиты в открытом виде — инфо
- Телефон, карта (16–19 цифр), ссылка хранятся в `users.payment_info` и `members.payment_info` JSON-ом, попадают в ежедневные бэкапы `/data/backups`. Видны только участникам группы (проверено), в историю пишется лишь факт изменения. Приложение не проводит платежи. Если растёт число пользователей, стоит рассмотреть шифрование поля или хотя бы маску номера карты в интерфейсе, а к бэкапам — права доступа на хосте.

### 15. Прочее — инфо
- `/version` отдаёт версию и sha, публично, не секрет.
- Базовый образ `node:24-slim` не закреплён по digest; рекомендуется Dependabot/Renovate для образа и экшенов.
- Участник может привязать к имени без Telegram свои реквизиты, и должники увидят их в группе. Это следствие модели доверия внутри группы.

## Проверено, проблем нет

- Аутентификация: `api.use('*')` проверяет подпись `initData` до любого обработчика; `/healthz`, `/version` и статика не отдают данных.
- Все маршруты `/api` (список ниже) проверены: маршруты группы идут через `loadGroupFor` (членство, иначе 404); тест на 21 маршрут от постороннего подтверждает 404 и отсутствие изменений.
- Подбор id: траты, участники и шаблоны ищутся с `AND group_id = ?`; чужие id в URL дают 404, в теле (плательщик, доли, шаблон) дают 400.
- initData: HMAC по спецификации Telegram, сравнение `timingSafeEqual`, `auth_date` проверяется (24 часа), пользователь обязателен.
- `DEV_AUTH`: по умолчанию выключен, в `docker-compose.yml` отсутствует, при включении есть предупреждение (см. п. 8 про усиление).
- Приглашения: код 72 бита случайных данных (`randomBytes(9)`), перебор нереален; превью отдаёт только название, валюту, число участников и свободные имена, без id и реквизитов.
- Токены привязки чата: 144 бита, одноразовые, 24 часа; превью показывает только название чата; `replaces` только участнику той группы.
- Утечки в ответах: `chat_id` в API не отдаётся (только название), реквизиты только участникам группы, лента изменений не содержит реквизитов, CSV строится из `groupDetail` для участника.
- SQL: все запросы параметризованные; единственные интерполяции в SQL — константа `REMIND_WINDOW_SQL` и путь бэкапа из конфигурации (проверка на кавычку есть).
- zod: длины имён (64), названий (100), массивов (50 и 100), сумм (до 1e12), строгая схема реквизитов (`.strict()`), перечисления для валюты, категории, режима.
- XSS в интерфейсе: нет `dangerouslySetInnerHTML`, `innerHTML`, `eval`; React экранирует названия и имена; `openLink` получает только `https://` ссылку, проверенную сервером (`normalizeLink`); ссылка «поделиться» собирается с `encodeURIComponent`.
- HTML в сообщениях бота: все пользовательские значения (названия групп, имена, названия трат) идут через `esc`; названия чатов отправляются без `parse_mode`; результаты inline берут `title` как обычный текст.
- CSV: значения, начинающиеся с `= + - @`, нейтрализуются; имя файла очищается.
- SSRF: внешний адрес один (`cbr-xml-daily.ru`), параметры проходят через перечисление валют и регулярное выражение даты.
- Права владельца: удалить группу может только владелец; уход передаёт владение.
- Напоминания: только кредитор из текущего плана, не чаще раза в сутки на пару.
- Инфраструктура: контейнер работает от пользователя `node`, в образе нет `node_modules` и исходников, `.dockerignore` исключает `.env`, `*.db`, `data`; токен бота не печатается; `npm audit` (включая `--omit=dev`): 0 уязвимостей.

## Маршруты API

Все под `/api`, все требуют `initData` и лимит 120 запросов в минуту на пользователя; без членства возвращают 404.

- Профиль: `GET /me`, `PUT /me`, `GET /me/payment-info`, `PUT /me/payment-info` (только свои данные).
- Группы: `GET /groups`, `POST /groups`, `GET|PATCH|DELETE /groups/:id` (удаление только владелец), `POST /groups/:id/export`, `/archive`, `/unarchive`, `/leave`.
- Участники: `POST /groups/:id/members`, `PATCH|DELETE /groups/:id/members/:memberId`.
- Чат: `GET /chat-links/:token` (токен), `POST /chat-links/:token/attach` (токен и членство в группе), `PUT /groups/:id/chat/feed`, `POST /groups/:id/chat/unlink`.
- Приглашения: `GET /invite/:code`, `POST /invite/:code/join` (по коду).
- Курсы: `GET /rates` (любой аутентифицированный; данные публичные).
- Траты: `POST /groups/:id/expenses`, `PUT|DELETE /groups/:id/expenses/:expenseId`.
- Регулярные: `GET|POST /groups/:id/recurring`, `PATCH|DELETE /groups/:id/recurring/:rid`.
- История: `GET /groups/:id/activity`.
- Напоминание: `POST /groups/:id/remind`.
- Вне `/api`: `GET /healthz`, `GET /version`, статика.
