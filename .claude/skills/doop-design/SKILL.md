# Дизайн в Doop

Doop — рабочая доска дизайна. Источник правды — репозиторий: `design/v1/README.md`, `design/v1/v1.css`, `web/src/tokens.css`, `web/src/ui.tsx`. Сначала дизайн согласуем на холсте с владельцем, потом пишем код.

Инструменты — MCP-сервер `doop` (через `execute`: `tools.doop.*`). Общие правила Doop — в его гайде: перед первым вызовом `tools.doop.get_guide({ topic: "doop-instructions" })`. Ниже — только то, что относится к нашему проекту.

## Холст

- `canvas_id`: `bCI9GJFCBF` — https://doop.design/c/bCI9GJFCBF
- Страницы: **«v1 · макеты»** (HTML-экраны, здесь работаем) и **«v1 · эталон»** (JPG из `design/v1/screens/` в той же раскладке — для сравнения, не править).
- Имена фреймов: `<N Группа> · <screen>`, эталоны — `… · эталон`. Группы-ряды сверху вниз: `1 Старт`, `2 Вход`, `3 Вкладки`, `4 Траты`, `5 Чек`, `6 Итоги`, `7 Настройки`. Шаг в ряду 430 px (фрейм 390 + 40), фреймы ряда выровнены по верху. Новый экран ставь в свой ряд, ничего не перекрывая.
- Гайды холста: `design-code-v1` (сжатые правила из README) и `v1-kit` (HEAD с токенами и классами `v1.css` + скрипт иконок). Их видят и встроенные агенты Doop.
- `agent_name` — `Claude` во всех вызовах; субагенты — `Claude · <роль>`.

## Как собрать экран

1. `get_canvas`, затем `get_guidelines({ name: "v1-kit" })` — markdown-строка с двумя блоками ```html: первый HEAD, второй ICONS.
   `const [head, icons] = [...md.matchAll(/```html\n([\s\S]*?)\n```/g)].map(m => m[1]);`
2. Документ: `<!doctype html><html lang="ru"><head>${head}</head><body style="margin:0"><div class="scr">…</div>${icons}</body></html>`. Тёмная тема — `<div class="scr dark">` и `<body style="margin:0;background:#000">`, иначе внизу белая полоса.
3. Только классы кита и токены `var(--…)`; инлайн-стили — тоже на токенах. Иконка — `<i data-i="food" data-s="22"></i>`, список имён — в конце `v1.css`. Образцы разметки бери из принятых фреймов (`get_frame` → `html`), а не изобретай.
4. Ширина 390, высота — по контенту (эталоны: 844–1829).
5. После каждого создания и правки — `get_frame_screenshot` (мелкие детали — `scale: 2`) и сверка с эталоном/замыслом по элементам сверху вниз: состав, тексты, цвета, выравнивание, отступы, низ под `.mbar`.

Мелкая правка — `edit_frame_html({ old_str, new_str })` (строка должна встречаться ровно один раз), большая — `set_frame_html`. Перемещение и имя — `update_frame`.

### Грабли, на которые уже наступили

- **₽ квадратом**: в шрифтах рендерера Doop нет знака. HEAD из `v1-kit` уже подгружает Inter только для ₽ (`text=₽`) — не выкидывай эту строку.
- Шрифт на холсте не SF Pro — небольшая разница в ширине текста допустима, всё остальное должно совпадать.
- Классы, которые путают: пунктирный чип — `chip dash`; чип с аватаром — `chip p`; плитка иконки в строке — `tile c-other` (у `tile sub` нет фона); шаги — `stepi`/`stepn`.
- Не вкладывать `<button>` в `<button>`: строки с кнопками внутри — `<div class="row">`.
- Если владелец двигает элементы в редакторе Doop, в HTML появляются инлайновые `position: relative !important; inset…`. Увидел такое в неожиданном месте — спроси, не случайно ли.
- Вложенных фреймов/групп в API нет: группировка — рядами и префиксом имени.

## Совместная работа с владельцем

- Задача на дизайн → `set_status` одной строкой → правка → скриншот → коротко, что изменилось.
- Комментарии на холсте: `get_comments`, ответ — `reply_to_comment`, закрыть — `resolve_comment`. Ссылка на элемент `/c/<canvas>?frame=<id>&selector=<css>` — найди элемент в HTML фрейма перед правкой.
- Решение владельца по вкусу («так лучше, чем…») — `save_decision`, чтобы холст помнил.
- Откат — `list_frame_versions` / `restore_frame_version`.
- Не удаляй и не переписывай чужие правки без вопроса; перед удалением фрейма посмотри на него.

## Из Doop в код

Берём в работу только фреймы со статусом **`ready_for_dev`** — его ставит владелец. Любая правка HTML или размера сбрасывает статус.

1. `get_canvas({ approval_status: "ready_for_dev" })`, затем `get_frame` — убедись, что статус всё ещё `ready_for_dev`, и возьми HTML.
2. Разбери, из каких компонентов собран экран. Есть новый компонент, токен или значение вне шкалы → **сначала** `design/v1/README.md` (правило, имя, таблица «экран → компоненты») и `design/v1/v1.css`, затем обнови гайды `v1-kit`/`design-code-v1` на холсте, чтобы они не разошлись с репо.
3. Обнови рендер в `design/v1/screens/<screen>.jpg` (780 px, ×2): `export_frame({ format: "jpg" })` или `get_frame_screenshot({ scale: 2 })`; проверь размер. Потом замени картинку на странице «эталон» (`upload_asset` + `set_frame_html` эталонного фрейма).
4. Код — по правилам `CLAUDE.md`: компоненты `web/src/ui.tsx`, токены `web/src/tokens.css`, тексты через i18n на двух языках, ветка и PR.
5. Сверь живой экран (`/?dev=1`, 375×812, светлая и `data-scheme="dark"`) с фреймом.

Обратное направление: поменялся дизайн-код в репо — обнови гайды холста и затронутые фреймы.

## Субагенты для пачки экранов

- Модель: `claude-code/claude-sonnet-4-6#medium`. `claude-sonnet-5-5` в этой конфигурации OpenCode не принимает изображения — не видит ни эталонов, ни скриншотов. Первым шагом субагент открывает картинку и, если не видит, останавливается.
- Бриф — [brief-template.md](brief-template.md): подставь экраны, координаты, `agent_name`, ссылки на принятые фреймы-образцы.
- Самоотчёт «совпадает» не принимать: каждый экран ревьюит оркестратор по скриншоту против эталона и возвращает список конкретных расхождений с замерами в px и ссылками на образцы. Мелочи быстрее поправить самому.
